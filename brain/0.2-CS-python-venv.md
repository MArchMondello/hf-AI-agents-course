# 0.2 Python venv — Cheat Sheet

*Part of hf-AI-agents-course-0-onboarding. A virtual environment ("venv") is a private Python for one project. Each project gets its own notebook, so packages never collide.*

## 1. The big idea in one picture

```
System Python (Ubuntu's)   ← don't touch: Ubuntu's own tools need it
│
├── ~/PROJECTS/hf-AI-agents-course/.venv   ← smolagents, litellm, ...
└── ~/PROJECTS/website/.venv               ← flask, ...
```

Each `.venv` folder holds its own `python` and `pip` plus the packages you install there. Delete the folder and the environment is gone. Nothing else is affected.

## 2. One-time setup (Ubuntu / WSL)

```bash
sudo apt update
sudo apt install -y python3-venv python3-pip
```

## 3. The daily workflow

```bash
# --- create (once per project) ---------------------------------
mkdir -p ~/PROJECTS/myproject
cd ~/PROJECTS/myproject
python3 -m venv .venv          # creates the .venv folder

# --- activate (every new terminal) -----------------------------
source .venv/bin/activate      # prompt now starts with (.venv)

# --- work ------------------------------------------------------
pip install requests           # installs ONLY into this venv
python main.py

# --- leave -----------------------------------------------------
deactivate
```

**Rule of thumb:** new terminal → `cd` into the project → `source .venv/bin/activate`.

## 4. Reading the prompt

```
(.venv) <user>@<hostname>:~/PROJECTS/hf-AI-agents-course$
└──┬──┘ └─┬──┘ └───┬────┘ └─────────────┬──────────────┘
 active  user   computer         current folder
 venv
```

`(.venv)` is a **badge** that tells you which Python is active. It is **not** your location. Your location is whatever comes after the colon.

## 5. Am I in the right venv?

| Check | Command | Good answer |
| --- | --- | --- |
| Prompt | look at it | starts with `(.venv)` |
| Where am I | `pwd` | your project folder |
| Which python | `which python` | `.../myproject/.venv/bin/python` |
| Which pip | `pip --version` | path ends in `.venv/...` |

If `which python` points to `/usr/bin/python3`, the venv is **not** active. Newer VS Code versions may activate the venv silently, without `(.venv)` in the prompt, so trust `which python` over the prompt.

## 6. Activate / deactivate ≠ install / uninstall

`activate` and `deactivate` work like a **light switch**. They change *which* Python your commands use, and nothing else.

```bash
source .venv/bin/activate   # ON : python/pip mean the venv's
deactivate                  # OFF: python/pip mean Ubuntu's again
source .venv/bin/activate   # ON again: every package is still there
```

The packages stay on disk in `.venv/lib/python3.X/site-packages/`. Behind the scenes, activation only adds `.venv/bin` to the front of `PATH`, the list of folders bash searches for commands.

**You never reinstall just because you deactivated.**

| Where | Venv activation |
| --- | --- |
| VS Code terminal (interpreter selected) | automatic |
| VS Code ▶ Run button | not needed (uses the venv's Python by full path) |
| Windows Terminal / plain Ubuntu | manual: `source .venv/bin/activate` |

## 7. When you DO reinstall

Only when the `.venv` folder itself is gone or no longer valid:

| Situation | Why |
| --- | --- |
| You deleted `.venv` | the packages were inside it |
| You **moved or renamed** the project folder | a venv stores its full path, so moving it quietly breaks it |
| The venv is broken or confused | it's quicker to rebuild than to repair |
| New computer / fresh clone | `.venv` is never copied or committed |

**Save your packages first (do this regularly):**

```bash
pip freeze > requirements.txt
```

**The rebuild recipe:**

```bash
deactivate                          # 1. switch off (skip if not active)
rm -rf .venv                        # 2. delete ONLY the venv folder
python3 -m venv .venv               # 3. create a fresh one
source .venv/bin/activate           # 4. switch on
python -m pip install --upgrade pip # 5. fresh pip
pip install -r requirements.txt     # 6. reinstall everything
```

**Renaming a project (example: `agents` → `hf-AI-agents-course`):**

```bash
deactivate
cd ~/PROJECTS
mv agents hf-AI-agents-course       # rename: files inside are kept
cd hf-AI-agents-course
rm -rf .venv                        # the old venv points to the old path
python3 -m venv .venv
source .venv/bin/activate
pip install 'smolagents[litellm]'   # or: pip install -r requirements.txt
```

`mv` = **rename/move** (nothing is lost). `rm -rf` = **delete forever** (no recycle bin). Always read what comes after it before pressing Enter.

## 8. Best practices

1. **One venv per project**, stored inside the project and named `.venv`. Editors (VS Code, PyCharm) find it automatically.
2. **Never commit `.venv` to git.** Add `.venv/` to `.gitignore`.
3. **Record your dependencies** in `requirements.txt` (see §7), so any rebuild takes one command.
4. **Treat the venv as disposable.** If it breaks, don't repair it. Rebuild it (§7).
5. **Never move a venv.** Rebuild it in the new place instead.
6. **Never use `sudo pip`.** If pip asks for sudo, you're not in a venv.
7. **Don't pass `--break-system-packages`** to get past an error. That error is protecting Ubuntu.
8. **Upgrade pip once** after creating a venv: `python -m pip install --upgrade pip`.
9. **Prefer `python -m pip`** over plain `pip` in scripts. It guarantees that pip belongs to the Python you're running.
10. **In WSL, keep projects in the Linux filesystem** (`~/PROJECTS`), not under `/mnt/c/...`. It's much faster, and file permissions work properly there.
11. **Quote extras in the shell:** `pip install 'smolagents[litellm]'`. Without quotes, bash may try to interpret the `[ ]`.

## 9. Common errors → fixes

| Error | Meaning | Fix |
| --- | --- | --- |
| `Command 'pip' not found` | pip not installed and no venv active | install `python3-pip`, then activate your venv |
| `externally-managed-environment` | trying to install into Ubuntu's Python | create/activate a venv |
| `.venv/bin/activate: No such file or directory` | wrong folder, or venv never created | `cd` into the project; `ls -a` to check for `.venv`; create it if missing |
| `ModuleNotFoundError` after installing | installed in one Python, running another | activate the venv, then `which python` |
| `ensurepip is not available` | `python3-venv` missing | `sudo apt install python3-venv` |
| venv "activates" but `python`/`pip` behave oddly after a rename | venv still points to the old path | rebuild it (§7) |
| `.venv (broken)` in VS Code's status bar | VS Code is running on Windows, not connected to WSL | `><` bottom-left → Reopen Folder in WSL |

## 10. Bonus: `uv`, the fast modern alternative

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
uv venv                 # creates .venv
uv pip install requests # very fast drop-in for pip
```

Same idea, same `.venv` folder, much faster. Learn plain `venv` first, then try `uv`.
