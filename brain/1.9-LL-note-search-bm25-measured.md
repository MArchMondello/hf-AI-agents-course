# 1.9 Lesson: Note Search, Measured — BM25F, a Held-Out Exam, and the Right Section

*Part of hf-AI-agents-course-1-agents. Follow-up of [1.8](1.8-LL-public-agent-codeagent-is-not-a-sandbox.md). The repo guide agent on my Space cited the wrong note for "What is the ReAct loop?". Instead of patching that one question, I built an evaluation set, measured the old search, replaced it with BM25F and measured again. Then I found that finding the right note is not enough: the agent must also read the right part of it. 22 Nov 2026.*

## 1. The big idea in one picture

```
 visitor: "What is the ReAct loop?"
    │
    ▼  model ──► find_brain_note("ReAct loop")
                   │   BM25F: every note gets a score
                   │     rare word ("react", few notes)  >>  common word ("agent", every note)
                   │     in the NAME x3 · in a HEADING x2 · in the TEXT x1, each discounted by its length
                   ▼
                 1.0-CS-agents  (+ 2 runners-up, each with its most telling line)
    │
    ▼  model ──► read_brain_note("1.0", topic="ReAct loop")
                   │   long note? → the "## " SECTION that matches best, not the first 2,500 characters
                   ▼
                 "## ReAct vs Chain of Thought: open loop or closed loop …"
    │
    ▼  final answer, with "Source: 1.0-CS-agents (link)"
```

**A search is a measuring instrument: calibrate it on known cases before trusting it.** One wrong answer is an anecdote (rule of [1.4](1.4-LL-weather-agent-persona-chat-template.md)); 42 questions with their expected notes are a test bench. And the bench has to include an exam I did not study for.

| Word | Meaning | Analogy |
| --- | --- | --- |
| **ranking** | ordering the notes by how well they answer a query | the order in which a librarian hands you the books |
| **idf** (inverse document frequency) | a word found in few notes says more than a word found in all of them | "Castell'Umberto" narrows a search; "Sicily" doesn't |
| **BM25** | the classic search-engine score: idf × a frequency that saturates, discounted for long documents | a juror who counts arguments, not how loudly they're repeated |
| **BM25F** | BM25 over fields (name, headings, text), each with its own weight and length discount | a title block weighs more than a note in the margin |
| **evaluation set** | queries with the note(s) that should come first | the test drawings a plotter must reproduce |
| **held-out set** | queries written *before* tuning, used once at the end | the exam, as opposed to the exercises |
| **top-1 / top-3** | the right note is first / among the first three | right on the first try / within three tries |
| **overfitting** | tuning until the exercises pass, without getting better in general | studying the answers instead of the subject |

## 2. The experiment

| Step | What |
| --- | --- |
| 1. Bench | 42 queries as a visitor or the model would send them ("ReAct agent", "How do I keep API keys out of a git repo?", ".env secrets"…), each with the acceptable top-1 notes. Notes read from a **frozen copy** of `brain/` (18 notes), so the world doesn't move between runs |
| 2. Baseline | the old search: 3 points per query word in the note's name + 1 per word in the text, ties by raw counts |
| 3. Diagnosis | look at every miss, write the cause *before* changing code |
| 4. Exam | 16 more queries written **before** tuning (`holdout`), sealed with a hash |
| 5. New search | BM25F + CamelCase split + plural folding + phrase bonus; a small grid on 4 parameters, keeping textbook values where they didn't matter |
| 6. Measure | both sets, old vs new; then a fresh adversarial review |

The bench lives in the Space (`tests/search_eval.py`); the raw results per query are in [`probe/1.9-note-search-bm25-runs.json`](../probe/1.9-note-search-bm25-runs.json).

## 4. Lesson 1: rare words carry the meaning

The old score gave every query word the same value. "agent" is in all 18 notes, "ReAct" in a few: for "ReAct agent", 1.6 won because "agent" was in its name. **idf** fixes that: a word's weight is `log(1 + (N − df + 0.5) / (df + 0.5))`, where `df` = how many notes contain it. With 18 notes: "agent" (df 18) ≈ 0.03, "react" (df 7) ≈ 0.9, "sequence" (df 1) ≈ 2.5.

The other ingredients, each with the miss that justified it:

| Ingredient | Miss it fixes |
| --- | --- |
| **saturation** (`K1`): the 10th "react" adds little | a note can't win by repeating a word |
| **fields**: name ×3, headings ×2, text ×1 | the title says what a note is *about* |
| **length discount per field** (`B`) | "agents" in a 1-word name (1.0) says more than in a 6-word name (1.8): fixed "what is an agent" |
| **plurals folded** ("agents" → "agent") | the query "agent" didn't match the name "agents" |
| **CamelCase split** (`ToolCallingAgent` → tool, calling, agent) | "tool calling agent" didn't find 1.8 |
| **phrase bonus**: all query words in a row in a title | "First Agent Template" vs 1.4's many "templates" |

## 5. Lesson 2: the exam you didn't study for

Tuning parameters on the same 42 queries you report is studying the answers. So: 16 queries written before tuning, used once. They caught two things the development set couldn't:

- the new search was **no better** on fresh queries at first (13/16 = 13/16): the gain was real but narrow;
- "what is an agent" failed on both versions: a common-word-only question, exactly what a visitor of a *course companion* asks. The fix (per-field length discount, a textbook BM25F feature, not a patch for that query) was decided **after** seeing the exam, so the exam is now "seen": the LL and the code say so.

Two exam entries were **my** mistakes, not the search's: `trust_remote_code` appears in no note (dropped), and "Ollama qwen local model" → 0.3 is a legitimate answer (the first local Qwen run), still counted as a miss because the expectation was written first.

## 6. Lesson 3: a point won by accident is a point to give back

An intermediate version split "ReAct" into "re" + "act", and "act" matched "Reason + **Act**" in 1.0: "ReAct framework" passed. Splitting a name into 2-letter pieces is wrong in general, so the rule became "split only if every part has 3+ letters" (`ToolCallingAgent` yes, `ReAct` and `OAuth` no). The score went 39 → 38. **A metric that rewards a bug is measuring the bug.**

## 7. Lesson 4: finding the note is not reading it

After the new search, "What is the ReAct loop?" found 1.0 — and the answer was still poor: *"The ReAct loop is not explicitly defined in the provided text"*. `read_brain_note` returned the first 2,500 characters, and the ReAct section is further down. So `read_brain_note(number, topic="")`: for a long note it returns the `##` section that best matches the topic (the same BM25F, run over the sections), plus the list of all sections. The prompt tells the model to pass the same keywords it searched with.

Before → after, same question, real model:

| | Answer |
| --- | --- |
| before | "…The ReAct loop is not explicitly defined in the provided text…" |
| after | "…an open loop: the model reasons, acts with a tool, reads the result… unlike Chain of Thought, a closed loop… a contract between the model and the code" (Source: 1.0). *Quoted as it was: the note then had "open" and "closed" swapped, fixed in 1.0 on 23 Nov 2026* |

Words that appear in every section ("agent") are ignored when choosing a section: they can't say *where* to look, so "what is an agent" reads 1.0 from the start, where the definition is.

## 8. Lesson 5: the review found what the bench couldn't

The fresh adversarial review (the 4th on this Space) found a bug no query had exposed: in 1.0, a ```` ``` ```` drawn inside an ASCII diagram, indented 38 spaces, was taken for the start of a code block. From there to the end, text and code were swapped: 56% of 1.0 was unreachable by any topic. The fix is the actual Markdown rule: a fence has **at most 3 leading spaces**, and only the same character, at least as many, closes it. Plus: no "…(truncated)" when nothing was cut, the section list cut between names, a cap on query length (a 4,000-character query took 0.9 s, now 39 ms) and a cache of the tokenized notes (12 ms per search).

## 9. Takeaways

- **Measure before and after**, on a frozen world, with the queries written down first.
- **Keep an exam you didn't study for**, and say so when you've seen it.
- **Rare words carry the meaning**: idf is one line of math and fixed the original bug.
- **Give back accidental points**: an honest 38 beats a lucky 39.
- **Retrieval has two halves**: the right note, then the right part of it.
- **Real-data tests are alarms, not gates**: the bench runs on the live repo with a margin (≥35/42), because a new note may legitimately move results.

## 10. Next probes

- `-es` plurals ("fixes", "branches") still don't fold: measure before adding rules.
- Synonyms ("stop sequence" ↔ `stop`): a keyword search can't; embeddings could. Worth it only if the bench shows misses of that kind.
- Cost: the agent now often does find → read → read → answer (4 steps = `max_steps`). Count steps and tokens on 10 questions, old vs new.

## 11. Common errors → fixes

| Error | Meaning | Fix |
| --- | --- | --- |
| a common word outranks a rare one | every word counts the same | idf (BM25) |
| a long note always wins, or always loses | no length normalization, or too much | per-field `B`; ours: 0.75 on names, 0.3 on headings and text |
| the right note, the wrong answer | the agent read the first part of a long note | read by section (`topic`) |
| half a note unreachable | an indented ```` ``` ```` taken for a code fence | the Markdown fence rule: ≤3 spaces, closed by the same character |
| "…(truncated)" on a complete section | marker added unconditionally | add it only when something was cut |
| the score improved, the search didn't | the metric rewarded a bug ("act" from "ReAct") | fix the bug, accept the lower score |
| results move without a code change | the bench reads the live notes | tests with a margin; re-measure, don't tune to the test |
