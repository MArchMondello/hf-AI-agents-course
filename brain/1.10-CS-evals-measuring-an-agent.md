# 1.10 Evals: Does the Agent Know What It Doesn't Know? — Cheat Sheet

*Part of hf-AI-agents-course-1-agents. Follow-up of [1.9](1.9-LL-note-search-bm25-measured.md). An eval is an exam for an agent: fixed questions, the behaviour you expect for each, a meter written as code, and one change at a time. Worked example: probe 1.10 on my Course Companion, after it answered my Unit 1 quiz questions with confident links to the wrong notes. 23 Nov 2026.*

## ⭐ The recipe in one line

**anecdote → hypotheses → questions with the expected behaviour → baseline + one-change variants → frozen world → raw answers → meter (code, checked by hand) → compare only what beats the noise**

## 1. The big idea in one picture

```
 QUESTIONS, each with the behaviour I expect           VARIANTS, one change each
 ┌──────────────────────────────────────────────┐      A  the agent as deployed (baseline)
 │ covered    → cite the right note              │      B  A + one sentence in the prompt
 │ cross      → read BOTH notes it needs         │      C  A + the search says how well it matches
 │ uncovered  → say "my notes don't cover this"  │
 └──────────────────────────────────────────────┘
                     │   × 3 runs each, all reading the same frozen notes
                     ▼
   RAW ANSWERS  ──────────►  METER (code)  ──────────►  TABLE  ──►  decision
   saved once, never edited      ▲   one label per answer
                                 │
                          checked by hand
```

**A demo shows that the agent *can* answer. An eval shows *how often* it does what it should, and whether a change made it better.** [1.9](1.9-LL-note-search-bm25-measured.md) measured the search (does the right note come first?). This one measures the **behaviour** (what does the agent do with what it finds, and with what it doesn't find?).

| Word | Meaning | Analogy |
| --- | --- | --- |
| **eval** | a fixed set of questions, an expected behaviour for each, and a way to score the answers | the inspection checklist at handover, not the guided tour |
| **expected behaviour** | what a good answer *does*, not its exact words (cite note 1.4; say it's not covered) | "the door opens outwards", not "the door is model X" |
| **baseline** | the system as it is, measured first | the survey of the existing building before the renovation |
| **variant** | the baseline with exactly **one** change | one design option, everything else equal |
| **abstention** | the agent says it doesn't know (here: "my notes don't cover this") | the consultant who says "not my field, ask a structural engineer" |
| **false source** | an answer that cites a note which doesn't contain it | a drawing stamped by an engineer who never saw it |
| **meter** (grader) | the code that gives each answer a label | the gauge on the test rig |
| **pilot** | a tiny run to check the pipeline and the meter before paying for the real one | the mock-up panel before ordering the façade |
| **frozen world** | everything the agent reads is identical in every run | testing all samples in the same lab, at the same temperature |
| **contamination** | the exam questions leaked where the system (or its builder) could learn them | the students had the exam paper the night before |
| **noise** | how much the score moves with no change at all | the tolerance of the instrument |

## 2. Why an eval, not a demo

The Course Companion looked fine in demos. Then I used it during the Unit 1 quiz (10 questions, asked as I would ask a colleague):

| What happened | How often |
| --- | --- |
| a good answer, from the right note | 4 |
| an answer to **another** question, with a confident `Source:` link (tokenizers → special tokens; tool design → sandboxes) | 3 |
| half right | 2 |
| broken (an empty, cut answer) | 1 |
| "my notes don't cover this" | **0** |
| more than one note read for a question | **0** |

That is an **anecdote**: one session, one person, one day. It's a question, not an answer (rule of [1.4](1.4-LL-weather-agent-persona-chat-template.md)). An eval turns it into numbers that can be compared before and after a change.

## 3. The method, step by step

| # | Step | In probe 1.10 |
| --- | --- | --- |
| 1 | **Write the hypotheses before measuring** | H1: it doesn't say when the notes don't cover a question. H2: it reads one note per question, never two. H3: the literal `\n` in lists are a formatting habit of the model, not something the prompt causes |
| 2 | **Write the questions, each with its expected behaviour** | 14 public questions: 6 that one note answers, 2 that need two notes, 6 that no note covers (checked with `grep` on the notes) |
| 3 | **Keep a private set** | the 10 quiz questions, labelled the same way, outside the repo: only totals are published (section 7) |
| 4 | **Baseline + one change per variant** | A as deployed · B + one sentence in the prompt · C + the search reports how many keywords each note contains |
| 5 | **Freeze the world** | the notes at one commit; live statistics off; the agent's own settings (model, temperature 0.5, max 4 steps) read from its code, not typed by hand |
| 6 | **Pilot first** | 1 question × 3 variants: the pipeline works, ~10,400 input tokens and ~8 s per run, and a surprise that changed the meter (section 6) |
| 7 | **Collect raw answers, measure separately** | the collect cell only saves answers; the measure cell reads the file. Fix the meter, re-measure, pay nothing |
| 8 | **Check the meter by hand** | read the answers the meter labels, especially the borderline ones (section 8) |
| 9 | **Compare only what beats the noise** | 3 runs per question: a difference of 1 or 2 answers out of 18 is noise; 10 out of 18 is not |

Where it lives: [`my-agents/First_agent_template/First_agent_template.ipynb`](../my-agents/First_agent_template/First_agent_template.ipynb), section 5 (parameters, collect, measure, what we found). Raw public runs: [`probe/1.10-knows-what-it-doesnt-know-runs.json`](../probe/1.10-knows-what-it-doesnt-know-runs.json). The agent's assessment, to pick up when improving it: [`EVAL.md`](../my-agents/First_agent_template/EVAL.md).

## 4. Results

216 runs, 0 errors. Llama 3.3 70B at temperature 0.5, max 4 steps, notes frozen at commit `34ddd1a`. "18" = 6 questions × 3 runs.

| | A as deployed | B + one sentence | C + match strength |
| --- | --- | --- | --- |
| Outside the notes: **says so, no source** | **0/18** | 3/18 | 1/18 |
| Outside the notes: says so, but cites a note | 6/18 | 6/18 | 7/18 |
| Outside the notes: **cites a note as if it answered** | **11/18** | 9/18 | 10/18 |
| Outside the notes, private quiz questions: says so at all | 0/9 | 0/9 | 0/9 |
| One note answers: the right note is cited (public · private) | 15/18 · 14/21 | 15/18 · 14/21 | 15/18 · 12/21 |
| Questions that need two notes: runs that opened both | 0/6 | 0/6 | 0/6 |
| Any question: runs that opened **two** notes | **0/72** | **0/72** | **0/72** |

| Hypothesis | Verdict |
| --- | --- |
| H1: it doesn't say when the notes don't cover a question | **confirmed**, with a nuance: when it notices, it says so *and cites the note anyway* |
| H2: it reads one note per question, never two | **confirmed**: 0 of 216 runs. Asked which model the Space uses, it read only the older note and answered "Qwen" 9 times out of 9 (the right answer, Llama, is in the newer note) |
| H3: the literal `\n` come from the model's formatting | **not decided**: they appeared only on the one question that asks for a list (4 of 9 runs) |

Two defects nobody was looking for, found by reading the answers: one answer cites a note that **doesn't exist** (`0.0-LL-tokenization-subwords`, with a made-up link), and 5 of 42 baseline runs cite a note they **never opened** (they saw only its one-line preview in the search results).

## 5. Lesson 1: the anecdote was a pattern, not bad luck

The private set is the quiz session, replayed. The failures came back **3 times out of 3, in every variant**: tokenizers → special tokens, tool design → sandboxes, "learning and adaptation" → ReAct, the benefits of agents → design rules. Even the broken answer (cut after a backslash) came back, 2 times out of 3 in A; in the other runs it listed its own tool outputs as "examples of observations", as during the quiz. At temperature 0.5 the three runs of one question almost always agree (`111`, `444`); the differences are *between* questions, not between runs.

**What it means for an eval:** when the system is this consistent, **more questions teach more than more repetitions**. Three runs are enough to see that it's stable; the next euro goes into new questions.

## 6. Lesson 2: "does it say so?" and "does it cite?" are two questions

The first meter had one question: *does it abstain?* The pilot (1 question × 3 variants) showed an answer that does both things at once: "MCP is not explicitly defined in the provided notes… Source: 0.3". So the meter became a 2 × 2 table:

| | no `Source:` | cites a note |
| --- | --- | --- |
| **says the notes don't cover it** | 1. clean (the goal) | 2. honest, but the link still lends authority |
| **doesn't say so** | 3. answers from general knowledge | 4. **false source**: the worst |

**What it means for an eval:** decide the categories from real answers (a pilot), not from the hypothesis alone. A label that mixes two behaviours hides the one you want to change.

## 7. Lesson 3: a rule can only fire on a gap the model can see

Variant B added one sentence: *"If the notes you read do not answer the question, say so plainly and do not cite them as Source."* Clean answers went from 0 to **3 out of 18**: two on byte-pair encoding, one on LlamaIndex. On the private quiz questions: 0 out of 9, as before. On the others the model didn't think there was a gap: it **bent the note to fit the question**. Asked about the KV cache (a memory inside the model), it explained the weather tool's HTTP cache from 1.4; asked about LangGraph, it answered with the closed loop of 1.0. Nine times out of nine each.

Analogy: telling a site manager *"if the drawing doesn't show it, say so"* doesn't help when he is sure the drawing shows it. The fix is upstream: the drawing must say what it doesn't cover (the tool), or someone must check (the code).

Variant C (the search says how many keywords each note contains) changed nothing beyond the noise. **What it means for an eval:** a variant that doesn't move the numbers is a result too: it tells you where the problem is *not*.

## 8. Lesson 4: the meter had a bug, and reading found it

The first table said C opened two notes in 14 runs, against 7 for A: "C makes it cross-reference". Reading the runs: those extra reads were `read_brain_note("0")` and `read_brain_note("1")`, numbers that open nothing. Counting only real notes: **0 in every variant**. The conclusion flipped. Because the collect cell saves raw answers and the measure cell only reads them, the fix cost nothing: change the meter, re-run the measure cell, no new runs.

**What it means for an eval:** the meter is code, and code has bugs. Read the answers behind every surprising number before believing it. Write down what was read by hand: here all 54 public answers outside the notes, all 18 two-note answers, all 27 private answers outside the notes, and samples of the rest.

## 9. Lesson 5: keep the exam private

The quiz answers are private by Hugging Face's choice. Publishing the 10 quiz questions with their labels would publish an answer key: unfair to the course, and exactly the "copy" I don't want to be suspected of. So the probe has **two sets**: a public one written by me (in the repo, with every answer), and the private quiz set (outside the repo: only ids and counts in the notebook).

This is also the general rule of evals: **a test set that leaks stops measuring.** If the questions end up where the system, or its builder, can learn them, a good score means "it saw the exam", not "it knows". Same idea as the held-out exam of [1.9](1.9-LL-note-search-bm25-measured.md).

## 10. Lesson 6: freeze the world, read the settings from the code

Every run read the notes at one commit, packed from the local git history, so a note edited during the probe could not change the answers. The collect cell **checks** that the agent read that exact commit, and takes the model, temperature and max steps **from the agent's code**, not from my memory. The probe file records them all, so in a month the numbers still say what they were measured on.

## 11. Takeaways

- **An eval is a checklist with expected behaviours, not a demo.** One good answer proves it *can*; 72 runs per variant say *how often*.
- **The anecdote first, then hypotheses, then the bench.** The quiz session was right about the pattern; the bench gave it numbers and found two defects it hadn't shown.
- **Categories come from a pilot.** "Says so" and "cites" are two questions.
- **One change per variant; a null result is a result.** B and C don't fix it: the problem is not what the model is told, it's what it can't see.
- **The meter is code: read by hand behind every surprise.** Here it flipped a conclusion.
- **Keep the exam private.** A leaked test set measures memory, not skill.
- **More questions beat more repetitions** when the system answers the same way every time.

## 12. Next probes

Each one re-runs this bench after one change to the agent (the list, with the causes in the code: [EVAL.md](../my-agents/First_agent_template/EVAL.md)):

- the agent may cite only notes that exist **and** that it opened (a check in the code, not a sentence in the prompt);
- the reading tool says which rare words of the question **don't appear** in the note (the drawing says what it doesn't cover);
- the reading tool lists the notes a note links to, and the agent gets two more steps to follow them;
- more questions, fewer repetitions: 30 questions × 1 run;
- the same bench on another model, to see which defects belong to the model and which to the design.

## 13. Common errors → fixes

| Error | Meaning | Fix |
| --- | --- | --- |
| "It works, I tried it" | a demo: one run, on a question you chose | a fixed set of questions with expected behaviours, measured before and after |
| One label for "abstains" | an answer can say "not covered" **and** cite a source | separate *says so* from *cites*; let a pilot show which categories exist |
| The meter's number is believed at once | the meter is code, and code has bugs | read the answers behind every surprising number; record what was read |
| A note changed during the probe | runs read different worlds; differences mean nothing | freeze: one commit for all runs, checked by the code |
| The exam questions are published with their answers | the set leaks: it measures memory, not skill | keep a private set; publish only counts |
| A variant changes two things | you can't tell which one worked | one change per variant, built by replacing text in the baseline + a check that it happened |
| A difference of 1 or 2 answers is reported as progress | that's the noise | look at the runs of each question: when they agree, add questions, not repetitions |
| The settings are typed into the report by hand | they drift from what really ran | read model, temperature and steps from the agent's own code, save them with the runs |
