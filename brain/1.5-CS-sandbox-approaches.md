# 1.5 Sandbox Approaches for Code Agents — Cheat Sheet

*Part of hf-AI-agents-course-1-agents. A Code Agent runs code written by a model: the question is not "if" it can do damage, but "where" that code runs and how far the damage can reach. Based on section 6 of `0.onboarding.ipynb` and the smolagents docs, [“Secure code execution”](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution), checked on `smolagents` 1.26.0: the error messages in section 7 are real, from creating a `CodeAgent` with each `executor_type` and no credentials.*

> 📚 **Main source:** smolagents documentation, [“Secure code execution”](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution). Sections 2–5 summarise it; quotes are marked “…”; the opinions in section 6 are ours.

## ⭐ The one thing you'll do most

Switch the executor with one argument, and always use the agent as a context manager, so the sandbox is cleaned up:

```python
with CodeAgent(model=model, tools=[], executor_type="e2b") as agent:   # "local" | "blaxel" | "e2b" | "modal" | "docker"
    agent.run("What is the 100th Fibonacci number?")
# leaving the `with` block = the sandbox is shut down (same as agent.cleanup())
```

## 1. The big idea in one picture

```
                                                                        Safer
──┼──────────────────┼────────────────────┼───────────────┼──────┼──────────▶
  │                  │                    │               │      │
Vanilla Python   With authorized     With fine-grained   Docker   E2B
interpreter      imports = "*"       authorizations
                 └──────────────┬───────────────┘        └───┬───┘
                    Default LocalPythonExecutor        Sandboxed execution
```

*(Diagram redrawn in text from the smolagents docs, [“Secure code execution”](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution).)*

| Word | Meaning | Analogy |
| --- | --- | --- |
| **executor** | the part of the agent that runs the code the model writes | the contractor who builds what's on the drawing |
| **`LocalPythonExecutor`** | smolagents' own interpreter, on your machine: runs the code operation by operation, only what is allowed | the site rulebook: works as long as everyone follows it |
| **sandbox** | an isolated place where the code runs: whatever it breaks, it breaks there | the site fence: the damage stays inside |
| **remote sandbox** | the isolated place is someone else's computer, in the cloud (Blaxel, E2B, Modal) | the test is done in an external lab, not in your office |
| **local sandbox** | the isolated place is a container on your own machine (Docker) | a fenced test area inside your own yard |
| **context manager** (`with`) | Python syntax that runs a cleanup when the block ends, even after an error | the site is cleared and handed back at the end of the job |

## 2. Why a sandbox at all

By default the `CodeAgent` runs the model's code **in your environment**. The docs list four ways it can go wrong:

| Risk | What happens |
| --- | --- |
| Plain LLM error | the model means well and writes a harmful command anyway |
| Supply chain attack | an untrusted or compromised model generates harmful code |
| Prompt injection | an agent browsing the web reads malicious instructions and follows them (see LL 1.3) |
| Publicly accessible agents | strangers craft inputs to make the agent run their code |

— *Source: smolagents documentation, [“Secure code execution”](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution).*

The `LocalPythonExecutor` blocks a lot (see `1.0-CS-agents.md`), but the docs are clear: “It’s important to understand that no local python sandbox can ever be completely secure.” Example from the docs: allow `Pillow` and the model could fill your disk with thousands of large images. That is perfectly legal code.

## 3. Two approaches: sandbox the code, or sandbox everything

```
APPROACH 1: only the code snippets            APPROACH 2: the whole agentic system
───────────────────────────────────           ────────────────────────────────────
YOUR MACHINE           SANDBOX                YOUR MACHINE        SANDBOX
┌──────────────┐       ┌────────────┐                             ┌──────────────────┐
│ agent        │ code  │            │                             │ agent            │
│ model calls  │──────▶│ runs code  │         starts it ────────▶ │ model calls      │
│ tools        │◀──────│            │                             │ tools            │
│ API keys     │output └────────────┘         API keys ─────────▶ │ runs code        │
└──────────────┘                                                  └──────────────────┘
executor_type="..."  (one argument)           manual setup (the docs show E2B and Docker)
```

| | Approach 1: code snippets | Approach 2: entire system |
| --- | --- | --- |
| Setup | one argument: `executor_type=...` | manual: start the sandbox, install smolagents in it, send the agent code |
| API keys | stay on your machine | must be sent into the sandbox |
| Multi-agents (managed agents) | ❌ not supported | ✅ |
| Isolation | the code only | everything: agent, model calls, tools |
| Docs' advice | good balance for simple agents | for complex multi-agent systems that need full isolation |

— *Source: smolagents documentation, [“Secure code execution”](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution).*

In approach 1 **the model is still called from your machine**, so in principle the local Ollama model works too: only the code travels. With approach 2, the sandbox would have to reach the model itself.

## 4. The four `executor_type`s

| `executor_type` | Where the code runs | You need | Notes from the docs |
| --- | --- | --- | --- |
| `"local"` (default) | your machine, inside `LocalPythonExecutor` | nothing | a rulebook, not a fence |
| `"blaxel"` | cloud VMs at blaxel.ai | account + `pip install 'smolagents[blaxel]'` + `BL_API_KEY` and `BL_WORKSPACE` (or `bl login`) | VMs wake from hibernation in under 25 ms and scale to zero when idle |
| `"e2b"` | cloud sandboxes at e2b.dev | account + `pip install 'smolagents[e2b]'` + `E2B_API_KEY` | the docs' main example, also for approach 2 |
| `"modal"` | cloud sandboxes at modal.com | account + `pip install 'smolagents[modal]'` + a Modal token | |
| `"docker"` | a container **on your machine** | Docker installed + `pip install 'smolagents[docker]'` | no account, no cloud; the docs also show it for approach 2, with a `Dockerfile` |

— *Source: smolagents documentation, [“Secure code execution”](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution).*

How to choose:
- **Cloud (Blaxel, E2B, Modal):** nothing to install apart from a `pip` extra, but you need an account and a key, the code leaves your machine, and the usage may cost money. Check the pricing first.
- **Docker:** everything stays local, no account. But you must install and run Docker (on WSL: Docker Desktop with WSL integration, or Docker Engine inside Ubuntu), which is a setup project of its own. [Install Docker on your system ](https://docs.docker.com/get-started/get-docker/)

> **Don't confuse:** `executor_type="docker"` puts **only the agent's code** in a container. A **devcontainer** puts **the whole development environment** (Python, `.venv`, tools) in a container. Same technology, different scale. Both are planned for later in this course project.

## 5. Best practices (Blaxel, E2B, Docker)

From the docs:

| Area | Practice |
| --- | --- |
| Resources | set memory and CPU limits; execution timeouts; monitor usage |
| Security | minimal privileges; no network access you don't need; secrets in environment variables, not in code |
| Environment | minimal dependencies; **pinned versions**; update base images regularly |
| Cleanup | always clean up (use `with`), so no dangling containers keep eating resources |

— *Source: smolagents documentation, [“Secure code execution”](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution).*

## 6. Where we are, and why Docker comes later

| Today (`0.onboarding.ipynb`) | Later |
| --- | --- |
| `LocalPythonExecutor`, no tools, no extra imports apart from `numpy` | an agent with tools that touch files or browse the web (prompt injection becomes real) |
| local model (qwen via Ollama), no keys to protect | API keys in `.env` (Claude, HF) |
| risk: low, and checked by hand (section 4 of the notebook) | → Docker: once, for both the devcontainer and `executor_type="docker"` |

Rule of thumb: **the fence goes up when the crane arrives**. Until the agent can reach the file system or the web, the rulebook is enough. Plan the fence in advance, though.

## 7. Common errors → fixes

| Error | Meaning | Fix |
| --- | --- | --- |
| `ModuleNotFoundError: Please install 'docker' extra to use DockerExecutor` | the `pip` extra for that sandbox is not installed | `pip install 'smolagents[docker]'` (quotes needed: `[ ]` mean something to bash) |
| e2b: `AuthenticationException: API key is required` | no `E2B_API_KEY` | create the key on e2b.dev, put `E2B_API_KEY=` in `~/PROJECTS/.env`, `load_dotenv()` before creating the agent |
| modal: `AuthError: Token missing` | no Modal token configured | create the account, then follow modal.com's token setup |
| blaxel: `RuntimeError: ... No Blaxel credentials found` | no `BL_API_KEY` / `BL_WORKSPACE` | set both in `.env`, or run `bl login` |
| `executor_type="docker"` can't connect | Docker not installed or not running | install Docker / start Docker Desktop, then `docker ps` should answer |
| `ValueError: Unsupported executor type` | typo in `executor_type` | one of `"local"`, `"blaxel"`, `"e2b"`, `"modal"`, `"docker"` |
| multi-agent setup fails in the sandbox | approach 1 doesn't support managed agents | approach 2: run the whole system inside the sandbox |
| sandboxes or containers left running (and billing) | the agent was not cleaned up | use `with CodeAgent(...) as agent:` or call `agent.cleanup()` |
| `InferenceClientModel()` fails with an auth error | it calls HF Inference Providers and, by default, looks for `HF_TOKEN` | ours is `HF_TOKEN_INFERENCE`: `InferenceClientModel(token=os.getenv("HF_TOKEN_INFERENCE"))` after `load_dotenv()` (see [0.8](0.8-CS-env-secrets.md)), or use your local `LiteLLMModel` (Ollama) |
