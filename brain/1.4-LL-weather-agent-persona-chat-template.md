# 1.4 Lesson: Maresciallo Costa — A Real Tool, a Persona and the Chat Template

*Part of hf-AI-agents-course-1-agents. Follow-up of [1.3](1.3-LL-lie-order-next-to-observation.md). Based on section 8 and BONUS 4 of `1.weather-agent-lab.ipynb` with local Qwen2 7B via Ollama, `temperature=1`, 20 Nov 2026.*

## 1. The big idea in one picture

```
 "What's the weather in Lyon?"
        │
        ▼
   LLM  ── understands, decides ──►  {"action": "get_humidity", "action_input": {"location": "Lyon"}}   fuzzy  → LLM
        │
        ▼
   code ── parses, checks, runs ──►  Open-Meteo API  ──►  "Lyon, ..., France: 67%"                    exact  → code
        │
        ▼
   LLM  ── writes the Final Answer, in the persona's voice                                             fuzzy  → LLM
```

**The prompt asks, the code guarantees.** Everything that has one right answer (coordinates, units, the format of an Action) belongs to code. The LLM gets only what needs judgment: which tool, which words.

| Word | Meaning | Analogy |
| --- | --- | --- |
| Tool | a Python function the agent can call; the LLM only sees its name, arguments and docstring | a specialist consultant: you read their business card, not their CV |
| Persona | the character in the system prompt (here a TV weatherman of the Aeronautica Militare) | the dress code of a firm: it changes the voice, and sometimes more |
| Chat template | the recipe that turns the `messages` list into **one string** of text for the model | the binding of a project folder: drawings, letters and minutes become one bound document |
| Template line | the format example in the prompt (`Final Answer: <...>`) | a sample sheet in the specification |
| Measuring tape | the code that counts results across runs | the surveyor's tape: if it is wrong, every drawing is wrong |

## 2. The real tool: `WeatherNow`

### API or web search?

| | **Weather API** (chosen) | **Web search** |
| --- | --- | --- |
| Returns | structured JSON: `{"temperature_2m": 11.5}` | free text, page snippets |
| Who parses | our code, deterministic | the LLM, can misread or invent |
| Good for | measurable data | open questions ("what is happening in Rome today?") |

[Open-Meteo](https://open-meteo.com): free, **no API key**, two calls: geocoding (city → lat/lon), then `current` weather (lat/lon → numbers).

### One fetch, three readings

```
get_temperature("Lyon")              chooses WHAT and HOW:  lambda d: f"{d['temperature_2m']:.1f} °C"
   └─► _read(location, country, formatter)     coordinates: asks the data, catches errors, adds the place name
          └─► _fetch(location, country)        procures: cache or 2 HTTP calls → dict
```

| Design choice | Why |
| --- | --- |
| **Cache** (10 min) | not to save tokens (the LLM reads the same text either way), but to save HTTP calls and, above all, for **consistency**: condition, temperature and humidity come from the *same* measurement |
| The answer **names the place found** (`Lyon, Auvergne-Rhône-Alpes, France: 67%`) | geocoding always finds *something*: "Atlantis" exists, in South Africa. The name makes a wrong city visible |
| Optional **`country`** (name, code or region) | "Paris" → France; `("Paris", "Texas")` → Texas. The LLM disambiguates, the code filters. A first version did `location.split(",")[0]` and threw "Texas" away |
| **`"temperature_unit": "celsius"`** in the request | the `" °C"` in the output is a label *we* write. Without asking explicitly, it relies on the API's default: a silent bug waiting to happen |
| Errors return a **sentence**, never a crash | the agent receives `Error: location 'Lyon' not found in 'Italy'` as an Observation and can react |

Why not let an LLM turn "Lyon" into coordinates? Because it would be slower, non-deterministic and could invent plausible coordinates with confidence. The linguistic work is already done upstream: the LLM wrote `"Lyon"` in the Action. What is left has one right answer.

## 3. Python patterns behind the tool

| Pattern | In the code | What it means |
| --- | --- | --- |
| `_underscore` | `_fetch`, `_read` | "internal, don't call from outside". A convention, not a lock: `meteo._fetch("Lyon")` works. Like the boiler room of a building: it runs everything, visitors don't go in |
| A function as an argument | `_read(location, country, formatter)` | `formatter` is a **parameter** like `location`, filled by the caller with a function. The shared part (fetch, errors, place name) is written once, only the formatting changes (DRY). A *higher-order function* |
| Docstring → description | `"""Current relative humidity in a city, in percent."""` | Python stores it in `func.__doc__`, the `@tool` decorator reads it. One source of truth for two readers: you and the LLM. So write it **for the LLM**: short, with the unit |
| Bound methods drop `self` | `tool(meteo.get_humidity)` | `inspect.signature` of a bound method shows only `location, country`: the course's decorator works unchanged |
| Dict vs list | `d["weather_code"]` vs `CONDITIONS[...]` | dict = drawers with labels, list = numbered seats. `d` is a dict, `CONDITIONS` a list of `(range, word)` pairs |

## 4. The system prompt writes itself

```python
tools_desc = "\n".join(f"- {t.to_string()}" for t in TOOLS)
COSTA_PROMPT = f"""... TOOLS:\n{tools_desc} ..."""
```

Add a tool to `TOOLS` → the prompt updates. Adding `get_wind_speed` takes three edits: **ask** the data (`current=...,wind_speed_10m` in `_fetch`), **read** it (the method), **give** it (`TOOLS`). One thing does not update: rule 3, *"call all **three** tools"*, written by hand. Hard-coded rules age when the code changes.

## 5. The loop by hand, and the ✂️ cut

The loop has the three guards of 1.3 (`stop=["Observation:"]`, JSON parsed and checked, `max_steps`). The first real runs found a fourth problem: **Qwen wrote three Actions in one output** (2 runs out of 4), against rule 1. The loop ran only the first, but the other two stayed in the history with no Observation, and at the next step the model got confused (empty output).

Fix in code: keep the output **only up to the end of the first JSON blob**. The model then sees a clean history (1 Action → 1 Observation) and gets back in line by itself.

## 6. BONUS 4: the experiment

The persona: *Maresciallo Costa, a precise weather officer of the Aeronautica Militare, on RAI 1*, plus:

```
4. In the Final Answer, speak like a calm TV weatherman for elderly Italian viewers,
   like my grandma used to watch: warm, slow, simple words.
...
Final Answer: {OPENING} <the weather in your calm TV tone, quoting the values from the Observations> {CLOSING}
```

with `OPENING = "Welcome to MeteoUno, in collaboration with the Aeronautica Militare."` and `CLOSING = "And now, after the weather in your city, a new episode of Don Matteo!"`.

One run kept the closing and **dropped the opening**, and invented *"a touch of breeze in their spring walks"* (no wind tool, and it is November). Three hypotheses: recency (the closing is the last line of the prompt), the tone "eats" the opening, or "Welcome" sounds wrong at step 4. So: **10 runs per variant, one change at a time.**

| Variant | Change | Tests |
| --- | --- | --- |
| A | the prompt as it is | baseline |
| B | rule 4 removed | does the tone eat the opening? |
| C | OPENING and CLOSING swapped in the template line | does the last phrase always win? |

**Main probe:** *"What's the weather like in Castell'Umberto right now?"*, a village of 1,300 people at 660 m in the province of Messina, Sicily. Weather **frozen** for all runs (cache set to 1 h: the consistency argument of section 2, used on purpose). Facts: `rain showers | 12.6 °C | 78%`. Raw answers: [`probe/1.4-costa-tone-and-phrases-castell-umberto-runs.json`](../probe/1.4-costa-tone-and-phrases-castell-umberto-runs.json).

**Backup probe:** the same 30 runs, a few hours earlier, on Lyon (`rain showers | 11.5 °C | 67%`): [`probe/1.4-costa-tone-and-phrases-lyon-runs.json`](../probe/1.4-costa-tone-and-phrases-lyon-runs.json). The city is one parameter at the top of the cell (`CITY`).

A detail on the way: the geocoder finds `Castell'Umberto`, but **not** `Castellumberto` or `Castell Umberto`. The code is literal: the LLM has to spell the name right.

## 7. The chat template: what Qwen really reads

Our `messages` is a Python list. The model never sees a list: Ollama **renders** it into one string with Qwen2's chat template (ChatML), then the model continues that string. Here is the real string at the last step of a run (template from Ollama: `curl localhost:11434/api/show -d '{"model":"qwen2:7b"}'`):

````
<|im_start|>system
You are Maresciallo Costa, ...                                          ┐
...                                                                     │ 501 tokens
Final Answer: Welcome to MeteoUno, ... <the weather in your calm TV     │
tone, ...> And now, after the weather in your city, a new episode ...   ┘ ← the template line
<|im_end|>
<|im_start|>user
Question: What's the weather like in Castell'Umberto right now?<|im_end|>   ┐
<|im_start|>assistant                                                       │
Thought: To answer the question, I need to check the current sky ...        │
Action:                                                                     │
```json                                                                     │
{"action": "get_condition", "action_input": {"location": "Castell'Umberto"}}│
```<|im_end|>                                                               │ ~300 tokens
<|im_start|>user                                                            │
Observation: Castell'Umberto, Sicily, Italy: rain showers<|im_end|>         │
<|im_start|>assistant                                                       │
Thought: Now that I know it's raining ... check the air temperature.       │
Action: ... {"location": "Castell'Umberto", "country": "Italy"} ...        │
...                                                                         │
Observation: Castell'Umberto, Sicily, Italy: 78%<|im_end|>                  ┘
<|im_start|>assistant
                                                     ← the model writes HERE
````

What this changes:

| Fact | Consequence for the experiment |
| --- | --- |
| The system prompt is **one block at the very top** | "the closing is the last line of the prompt" is true only *inside* that block: about 200–300 tokens of conversation (207 in a Lyon run, 297 in a Castell'Umberto run) sit between it and the writing point. Recency in the strict sense does not apply |
| What sits closest to the writing point are the model's **own** turns (Thought/Action) and the Observations | the most recent "examples" of how to write contain no phrases and no tone at all |
| When the model writes `Final Answer:`, those exact words appear **once** earlier in the string, followed by the OPENING | **models are good at "continue the way these same words continued before" (copying)**. In Lyon this fit (7/10 openings at the very start); in Castell'Umberto it did not (1/10). Copying is a tendency, not a mechanism to rely on |
| Observations travel as **`user`** messages (notebook cell 15) | to the model, the tool result is something "the user said", not a separate source |
| The template has **native tool support** (`<tool_call>`, role `tool`) that we don't use | our agent does tool calling **in plain text** (ReAct). Native tool calling is what `smolagents`' `ToolCallingAgent` uses: the model is trained on that format |
| The model learned these markers (`<\|im_start\|>`, roles) in training | the same words can weigh differently in a system block and in a user turn: the *role* is part of the text the model reads |

## 9. Lesson 1: one run is an anecdote, and so is one input

The run that started this (closing present, opening missing) turned out to be **1 time in 10** in Lyon. So far, the classic lesson.

Then the same 30 runs on another city turned 8/10 openings into **1/10**. With 10 runs that gap is far beyond noise: something in the *input* changed the behaviour, and we don't know what. Maybe the Italian place name, maybe "Sicily, Italy" in the Observations, maybe the longer Thoughts the model wrote.

**A prompt validated on one input is not validated.** A probe measures the prompt *on that input*. Test on several inputs before believing a percentage, the way a structure is checked under several load cases, not one.

## 10. Lesson 2: a template line shows, a rule commands (a necessary rule, not a sufficient one)

The hypothesis "the tone eats the opening" is **wrong, the opposite is true**. Without rule 4, the phrases vanish completely in both cities: **0/20**, even though the template line still contains them word for word.

Rule 4 is the only instruction that says ***"In the Final Answer…"***. Without it, the template line reads like a format description, a sample sheet nobody said to follow to the letter. With it, the Final Answer becomes something to perform. **But** whether the model *then* performs it swings from 8/10 to 1/10 with the input (lesson 1): the rule is **necessary, not sufficient**.

## 11. Lesson 3: position, no conclusion

The swap (C) was meant to test "the last phrase always wins". The two cities disagree: in Lyon C had *fewer* openings than A (2 vs 8), in Castell'Umberto *more* (5 vs 1), at the start and at the end. Don Matteo never moved to the start in either city (0/20).

The only stable fact: **the model never says "Don Matteo" first.** Meaning beats the template there. For the rest, position effects drown in the input effect of lesson 1. *Inconclusive* is a valid result: better written down than forced.

## 12. Lesson 4: a persona leaks into everything

Rule 4 asked for a *tone*. It got much more, in both cities:

- **Language:** Italian answers to an English question, 3/10 (A) and 3/10 (C) here, 5/10 and 2/10 in Lyon, **never** in B (0/20). B keeps "Aeronautica Militare, on RAI 1": the trigger is rule 4's *"elderly Italian viewers… my grandma"*.
- **Paraphrase:** across 60 runs, a phrase is copied exactly **2 times**. The model keeps the *spirit*: *"Benevenuto a MeteoUno"*, *"Prima del prossimo episodio di Don Matteo…"*, *"Welcome to MeteoUno, where we provide you with the most accurate weather information"*. If the exact text matters, **the code must append it**.
- **Facts, not numbers:** numbers are right **60/60**. Rule 2 says *"every **number** must come from an Observation"*, and the model took it literally. Words are not protected. In Castell'Umberto the Italian turned clumsy (*"grumi di pioggia"*, *"un temporeggiamento di 12.6 gradi"*) but no fact was invented. Lyon was worse:
  - *"La pioggia ha preso il controllo di Lyon **nel Sud-Ovest**"*: Lyon is in the east of France;
  - *"Il tasso di umidità è **altissimo**, a 67%"*: 67% is not very high;
  - *"Piove qualche **temporale** … aria più fresca **rispetto al solito**"*: no thunderstorm, and no tool knows "the usual";
  - and the very first run: *"a touch of **breeze** in their **spring** walks"*.

  B (no tone) invents nothing in either city. **The more personality, the more "creative" the words.** Same family as the gap-filling in [1.1](1.1-LL-dummy-agent-temperature.md).

## 13. Lesson 5: the measuring tape is code too

The automatic count was wrong **three times**:

- *"11,5 gradi"*: the Italian decimal comma, read as two numbers `11` and `5`;
- *"temporale"*: the list of invented words was English-only, and the model switched to Italian;
- *"**vent**uring out"*: the Italian stem `vent` (for *vento*, wind) matched an English word. Fixed to `vento`.

Fix: the experiment cell only **collects** raw answers into `probe/`, the next cell **measures** them. A wrong tape is fixed by re-running only the measuring cell, without 15 minutes of LLM calls. And every metric gets a reading by hand before it goes into a lesson.

## 14. Takeaways

1. **The LLM decides, the code executes.** Coordinates, units and formats go to code; judgment goes to the LLM.
2. **The prompt asks, the code guarantees.** Three Actions at once → cut in code. Exact phrases → append in code: the prompt delivered them 8/10 on one city and 1/10 on another.
3. **The model reads one string, not a list.** The chat template decides what is "near" and what is "far". A system prompt is always far by the last step.
4. **One run is an anecdote, one input too.** Probe several inputs before trusting a percentage.
5. **A template line shows, a rule commands**, but the rule is necessary, not sufficient (0/20 without it).
6. **A persona leaks**: into language, wording and facts. Protect *facts*, not just *numbers*.
7. **Collect raw, measure later**, and check the tape by hand.

**Next probes:** the same 30 runs on 3–5 cities (Italian and foreign names) to find what flipped 8/10 into 1/10; rule 2 rewritten as *"every **fact** (numbers, places, weather words)…"*; the phrases appended by code; the same probes with `BACKEND = "claude"`; native tool calling (`<tool_call>`) vs text ReAct.

## 15. Common errors → fixes

| Error | Meaning | Fix |
| --- | --- | --- |
| The tool answers for the wrong city | geocoding picks the most relevant name ("Paris" → France) | pass `country`; return the resolved place name so the mistake is visible |
| `location 'Castellumberto' not found` | the geocoder is literal: the apostrophe is part of the name | spell it as the official name; the error sentence lets the agent retry |
| `Error: 'wind_speed_10m'` after adding a tool | the method reads a key the request never asked for | add the variable to `current=` in `_fetch` |
| The model writes several Actions in one output | a small model ignores "one action per step" | keep only the first JSON in the history (cut in code) |
| A phrase in the template line never shows up | an example without a rule pointing to it | add an explicit rule ("In the Final Answer…"), or append the phrase in code |
| The prompt works on one input, fails on another | the probe measured one input, not the prompt | probe several inputs; guarantee critical output in code |
| The agent answers in another language | the persona implied it ("Italian viewers") | state the output language explicitly in the rule |
| Right numbers, wrong adjectives ("very high", "south-west") | rule 2 protects numbers only | extend the rule to facts; validate the answer against the Observations in code |
| "11,5" counted as wrong, Italian words missed, "venturing" counted as wind | the measuring tape assumed English, stems too short | collect raw answers, measure in a separate cell, read a sample by hand |
| Hand-written "call all three tools" after adding a 4th | a rule hard-coded next to generated text | generate it too: `{len(TOOLS)}` |
